## ۱. مقدمه

این دیاگرام ترتیب تعاملات بین اجزا را در یک سناریو نشان می‌دهد. در سیستم رستوران‌یار، ترتیب تعاملات برای هر سناریو (ثبت سفارش، مشاهدهٔ منو، پیگیری سفارش و ...) مشخص شده است.

---

## ۲. سناریو: ثبت سفارش با QR

### ۲.۱ Actors

| Actor | نقش |
|--------|------|
| مشتری | کاربر نهایی |
| Frontend | React (SPA) |
| Backend | Python + FastAPI |
| Database | PostgreSQL |
| KDS | نمایشگر آشپزخانه (Socket.io) |

### ۲.۲ ترتیب

1. مشتری QR روی میز را با موبایل اسکن می‌کند
2. Frontend درخواست `GET /api/tables/qr/{code}` به Backend می‌فرستد
3. Backend کد QR را اعتبارسنجی می‌کند
4. Backend منو را از Database می‌خواند
5. Backend شمارهٔ میز و لیست منو را برمی‌گرداند
6. Frontend منو را با شمارهٔ میز نمایش می‌دهد
7. مشتری غذاها را انتخاب و تعداد را تعیین می‌کند
8. مشتری روی «تأیید سفارش» کلیک می‌کند
9. Frontend درخواست `POST /api/orders` به Backend می‌فرستد
10. Backend درخواست را با Pydantic اعتبارسنجی می‌کند
11. Backend موجودی مواد اولیه را در Database چک می‌کند
12. Backend تراکنش را شروع می‌کند (BEGIN)
13. Backend سفارش را در جدول `orders` ثبت می‌کند
14. Backend اقلام را در جدول `order_items` ثبت می‌کند
15. Backend موجودی `ingredients` را کاهش می‌دهد
16. Backend تراکنش را تأیید می‌کند (COMMIT)
17. Backend با Socket.io اعلان به KDS می‌فرستد
18. Backend شمارهٔ سفارش را برمی‌گرداند
19. Frontend پیام موفقیت و شمارهٔ سفارش را نشان می‌دهد
20. KDS سفارش جدید را به آشپز نمایش می‌دهد

## ۳. سناریو: مشاهدهٔ منو

### ۳.۱ ترتیب

1. مشتری وارد صفحهٔ منو می‌شود
2. Frontend درخواست `GET /api/menu` به Backend می‌فرستد
3. Backend لیست غذاهای موجود را از Database می‌خواند
4. Backend لیست را با دسته‌بندی برمی‌گرداند
5. Frontend منو را نمایش می‌دهد

## ۵. سناریو: تحویل سفارش آنلاین به پیک (نقش گارسون)

### ۵.۱ ترتیب

1. گارسون صفحهٔ سفارش‌های آنلاین را باز می‌کند
2. Frontend درخواست `GET /api/waiter/online-orders` می‌فرستد
3. Backend سفارش‌های آماده را از Database می‌خواند
4. Backend لیست را برمی‌گرداند
5. Frontend سفارش‌ها را نمایش می‌دهد
6. گارسون روی «تحویل به پیک» کلیک می‌کند
7. Frontend درخواست `PUT /api/waiter/orders/{id}/hand-to-driver` می‌فرستد
8. Backend زمان تحویل را ثبت می‌کند
9. Backend وضعیت سفارش را به «در حال ارسال» تغییر می‌دهد
10. Backend با Socket.io به مشتری اعلان می‌فرستد
11. Frontend پیام موفقیت نشان می‌دهد

## ۶. سناریو: محاسبهٔ حقوق کارمندان

### ۶.۱ ترتیب

1. مدیر در پنل، دورهٔ محاسبه را انتخاب می‌کند
2. Frontend درخواست `POST /api/admin/payroll/calculate` می‌فرستد
3. Backend شیفت‌های کارمندان را از Database می‌خواند
4. Backend اضافه‌کاری را محاسبه می‌کند
5. Backend کسورات (غیبت) را اعمال می‌کند
6. Backend حقوق خالص را محاسبه می‌کند
7. Backend فیش حقوقی را در `payrolls` ذخیره می‌کند
8. Backend لیست فیش‌ها را برمی‌گرداند
9. Frontend فیش‌ها را نمایش می‌دهد

## ۷. خطاهای ممکن

| خطا | کد HTTP | رفتار سیستم | راهکار |
|------|---------|--------------|--------|
| QR نامعتبر | ۴۰۰ | پیام: «کد میز معتبر نیست» | نمایش پیام + پیشنهاد تماس با گارسون |
| موجودی کافی نیست | ۴۰۰ | پیام: «این غذا موجود نیست» | پیشنهاد غذای جایگزین |
| سفارش تکراری | ۴۰۹ | پیام: «این سفارش قبلاً ثبت شده» | جلوگیری از دوبار کلیک روی دکمهٔ تأیید |
| عدم احراز هویت | ۴۰۱ | هدایت به صفحهٔ ورود | ورود مجدد |
| خطای سرور | ۵۰۰ | پیام: «لطفاً دوباره تلاش کنید» | Retry خودکار با حداکثر ۳ تلاش |
| قطعی اینترنت | — | ذخیرهٔ سبد در localStorage | همگام‌سازی پس از اتصال مجدد |
| منقضی شدن JWT | ۴۰۱ | تلاش برای Refresh Token | در صورت شکست، هدایت به صفحهٔ ورود |

## ۸. نکات طراحی

### ۸.۱ تراکنش دیتابیس
ثبت سفارش و کاهش موجودی در **یک تراکنش** انجام می‌شوند تا اگر یکی خطا دهد، کل عملیات Rollback شود.

### ۸.۲ اعلان بلادرنگ
استفاده از **Socket.io** برای ارسال اعلان فوری به آشپزخانه (KDS) و پیک، بدون نیاز به Refresh.

### ۸.۳ اعتبارسنجی در سمت سرور
همهٔ ورودی‌ها با **Pydantic** اعتبارسنجی می‌شوند تا از حملات و داده‌های نامعتبر جلوگیری شود.

### ۸.۴ مدیریت خطا
هر خطای احتمالی با کد HTTP مناسب و پیام فارسی برگردانده می‌شود تا تجربهٔ کاربری حفظ شود.
